# Личные планеры и общие задачи

## Поведение

Один адрес приложения и одна база. Каждый входит своим паролем в свой профиль.
Личные проекты, задачи, расписание, деньги, дневник, клиенты и настройки видит только владелец.
При создании проекта или отдельной задачи можно выбрать «Личное» или «Общее».
Оба участника видят и редактируют общие объекты. Задачи общего проекта наследуют его доступ.
Личные события другого участника показываются только интервалом «Занято», без названия и подробностей.
Общее дело можно поставить или переместить только в интервал, свободный у обоих.

## 1. Надёжный запуск и перенос базы

- Сервер запускается после миграций; неудачная миграция останавливает запуск.
- Readiness проверяет схему, а не только соединение с MySQL.
- Сохранить резервную копию перед изменением владения записями.
- Все уже существующие данные назначить первому профилю; второму создать пустой планер.
- Расписание 508 и понедельничный шаблон принадлежат первому профилю, а не всем новым пользователям.

## 2. Аккаунты и сессии

- Таблица users: id, имя, хеш пароля, версия сессии, даты создания/изменения.
- Хранить только хеши паролей с индивидуальной солью; сравнение и ограничение попыток на сервере.
- Первому профилю назначить существующий PLANNER_PASSWORD через одноразовую инициализацию.
- Первый пользователь создаёт приглашение для друга; друг задаёт имя и пароль самостоятельно.
- Одноразовые приглашения имеют срок действия; открытой регистрации нет.
- Подписанная HttpOnly-сессия содержит userId и версию сессии. Выход и смена пароля отзывают сессии.
- Старые общие сессии после обновления перестают действовать; нужен повторный вход.

## 3. Владение данными и серверные проверки

- Добавить ownerId к личным данным всех модулей, включая настройки, шаблоны, завершения дня и журналы операций.
- Для завершения дня заменить ключ day на составной ownerId + day.
- Во всех чтениях bootstrap, аналитики и API модулей проверять владельца.
- Во всех изменениях проверять владельца по записи из базы, независимо от переданного клиентом UUID.
- Проверять связи: личная задача не может ссылаться на чужой личный проект, подзадачу или зависимость.
- Не отдавать личные записи через экспорт, ошибки, таймеры, поиск, графики или повтор офлайн-очереди.

## 4. Общие проекты и задачи

- Добавить общее пространство с двумя участниками: workspace и workspace_members.
- У проектов и задач хранить ownerId и необязательный workspaceId; scope выводится из этих полей.
- Задачи и этапы общего проекта наследуют workspaceId. Отдельная общая задача может существовать без проекта.
- У обоих участников одинаковые права редактировать общие названия, сроки, подзадачи и статус.
- Переход «личное → общее» показывать явно; не переносить автоматически личные заметки и финансовые записи.
- Возврат общего объекта в личный ограничить владельцем с проверкой связанных объектов.
- Добавить updatedAt/revision для отклонения устаревшего изменения; показывать предложение обновить данные.

## 5. Общие свободные часы

- Рассчитывать занятость каждого участника по его событиям, исключениям расписания и закреплённым блокам.
- Учитывать timezone каждого профиля, пересечение полуночи, дату и чётность недели.
- API для второго участника возвращает только начало/конец занятости, без личных названий и ID событий.
- Для общей задачи показывать пересечение свободных окон обоих участников.
- При планировании и drag-and-drop повторно проверять пересечения на сервере в транзакции.
- Блокировать планирование участников в стабильном порядке, чтобы два одновременных переноса не заняли одно окно.
- При конфликте сохранять прежнее положение и объяснять, чей интервал занят, без раскрытия личных деталей.
- Если участник позже добавляет личное событие поверх общей задачи, показать конфликт и предложить новый общий слот.
- Друг не может редактировать, удалять или перемещать личные события владельца через UI или API.

## 6. Интерфейс и локальные данные

- Вход по паролю и настройка имени профиля; выход и смена пароля в настройках.
- Переключатель «Личное / Общее» в создании проекта и задачи; отметка общего доступа на карточках.
- Фильтры «Мои / Общие / Все доступные»; отдельная отметка общих событий в календаре.
- Кэш запросов, localStorage, офлайн-очередь, отмена drag-and-drop и таймеры разделяются по userId.
- При выходе очищать данные предыдущего аккаунта из памяти и запрещать отправку его очереди от нового пользователя.
- Повторы общего шаблона создаются один раз на пространство и дату, с отдельными подзадачами.

## 7. Проверка и выпуск

- Два профиля: проверить отсутствие чужих личных данных во всех API и страницах.
- Попытка изменить чужую запись прямым UUID должна отклоняться.
- Общая задача и её пять подзадач появляются у обоих; изменения и конфликты версий обрабатываются.
- Проверить перенос в свободное окно, отказ в занятом, одновременные переносы и разные часовые пояса.
- Проверить обновление существующей базы без потери данных и повтор миграции.
- Проверить выход/смену аккаунта с офлайн-очередью, старой вкладкой и активным таймером.
- После проверки типов, тестов и сборки выпустить одним приложением и одной MySQL; две отдельные базы для совместных объектов больше не нужны.

Порядок реализации: запуск и миграции → аккаунты → владение всеми данными → общие проекты/задачи → совместное планирование → интерфейс и приёмка.
Разделение аккаунтов нельзя выпускать частично, пока хотя бы один модуль остаётся без проверки владельца.
